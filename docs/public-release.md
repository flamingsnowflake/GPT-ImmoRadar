# Preparing a Public Release Safely

## Principle

Do not flip the historical production repository from private to public.

The safe publication boundary is a **new repository created from a sanitized, history-free snapshot**. The private repository remains the complete operational history; the public repository contains only source/configuration examples that were intentionally selected for publication.

This is stronger than merely scanning the current branch: an old private commit can contain information that no longer exists in the current tree.

## Threat model

A real home-search installation naturally accumulates private data:

- e-mail credentials and Telegram/API tokens;
- listing e-mails and browser captures;
- exact property candidates, addresses and coordinates;
- database rows describing the user's search/history;
- Telegram sessions/chat IDs;
- machine hostnames, usernames and filesystem paths;
- reverse-proxy/internal-domain details;
- private contact addresses embedded in HTTP User-Agent strings;
- backups and debugging output.

None of this is required for an open-source release.

## Public/private split

### Keep private

```text
.env
config/browser_enrich_token
private/
secrets with real values
data/
*.sqlite*
archived mail
browser-enrich-inbox/
Telegram *.session
backups and Git bundles
production reverse-proxy config containing private hostnames
production userscript endpoint configuration
operator-specific property database/search history
```

### Publish

```text
application source
unit tests
Docker/Compose definitions after audit
configuration examples/default scoring rules
schema/migration logic
generic systemd service template
generic Tampermonkey source
architecture/operations/security documentation
```

Large external geodata such as `.pbf` files should be downloaded/generated by setup instructions rather than committed.

## Credentials

Before the first public release, rotate credentials that have ever appeared in terminal/debug output as defense in depth. This applies even if a repository scan shows those values were never committed.

Never “redact” a secret by committing a replacement on top of a public history that already contains the secret. History must be rewritten or, preferably for this project, omitted entirely from the new public repository.

## Production-specific strings

A public export should fail or sanitize known deployment identity such as:

- private host/domain names;
- personal e-mail/contact strings;
- home usernames/hostnames;
- absolute paths containing personal usernames.

Generic paths such as `/opt/immobilien-monitor` are acceptable documentation defaults.

The Nominatim User-Agent must use a configurable contact string rather than a personal address baked into public source.

## Tampermonkey

The private repo preserves the exact tested production 1.3.3 build.

The public userscript must **not** default to the production server. It should require/configure the user's own endpoints and tokens. A safe public default is an invalid/example URL or an explicit first-run configuration prompt.

This prevents a fork from accidentally transmitting someone else's viewed listing data to the original operator.

## Portal data

Do not publish captured listing pages, archived listing e-mails or a populated property database as project fixtures.

Tests should use synthetic/minimized fixtures that contain only the text necessary to exercise parsing behavior.

The project is not affiliated with listing portals. Users are responsible for portal terms, applicable law, data protection and respectful request rates. The preferred browser workflow operates on a page the user intentionally opened in their own browser; it should not be presented as a mechanism for bypassing access controls.

## Repeatable export

Use:

```text
tools/export_public_snapshot.py
```

The exporter is designed to copy only tracked source into a fresh directory, remove known private/runtime paths, neutralize deployment-specific strings, and fail on high-confidence secret/private patterns.

After export:

```bash
cd /path/to/public-export

git init
git add .
git diff --cached --check
```

Then run an independent secret scanner before the first public push. Recommended choices include Gitleaks or TruffleHog, plus a manual review of:

```bash
git grep -nEI \
  'password|passwd|secret|token|api[_-]?key|BEGIN .*PRIVATE KEY|@.*\.'
```

Do not blindly treat every `TOKEN_KEY` source-code symbol as a secret; verify actual values.

## Fresh public repository

Create the public repository empty and push the sanitized snapshot as its first commit. Do not import/clone the production repository's `.git` directory and do not use GitHub's “change visibility to Public” button on the production archive.

Suggested release workflow:

```text
private production repo
        │
        ├─ backup/checkpoint
        ├─ tests
        └─ export_public_snapshot.py
                  │
                  ▼
          sanitized directory
                  │
           independent scan
                  │
                  ▼
         NEW public repository
          first clean commit
```

## Final pre-public checklist

- [ ] Production DB/backups excluded.
- [ ] E-mail archives/browser inbox excluded.
- [ ] No real `.env`, token, password, session or private key.
- [ ] No personal contact/hostname that was not intentionally chosen for publication.
- [ ] Public Tampermonkey endpoint is configurable and not the production server.
- [ ] Synthetic tests contain no private listing/user data.
- [ ] Independent secret scanner reports clean or all findings are manually explained.
- [ ] `README.md`, install docs and security notes match the public configuration.
- [ ] GPL-3.0 license included.
- [ ] New public repository has no private production Git history.
- [ ] Credentials that appeared in historical debug output have been rotated.
