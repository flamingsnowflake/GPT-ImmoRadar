# Preparing a Public Release Safely

## Principle

Do not flip the historical production repository from private to public.

The safe publication boundary is a **new repository created from a sanitized, history-free snapshot**. The private repository remains the complete operational history; the public repository contains only source/configuration examples that were intentionally selected for publication.

This is stronger than merely scanning the current branch: an old private commit can contain information that no longer exists in the current tree.

## Threat model

A real home-search installation naturally accumulates private data:

- e-mail credentials and Telegram/API tokens;
- listing e-mails and browser captures;
- exact property candidates, addresses and coordinates;
- database rows describing the user's search/history;
- Telegram sessions/chat IDs;
- machine hostnames, usernames and filesystem paths;
- reverse-proxy/internal-domain details;
- private contact addresses embedded in HTTP User-Agent strings;
- backups and debugging output;
- regression tests or fixtures copied from real listings.

None of this is required for an open-source release.

## Public/private split

Keep private:

```text
.env
config/browser_enrich_token
private/
data/
*.sqlite*
archived mail
browser-enrich-inbox/
Telegram *.session
backups and Git bundles
production reverse-proxy configuration
production userscript endpoint configuration
operator-specific property/search history
production-derived test fixtures
```

Publish:

```text
application source
Docker/Compose definitions after audit
configuration examples/default scoring rules
generic systemd service template
generic reverse-proxy example
generic Tampermonkey source
architecture/operations/security documentation
synthetic tests/fixtures when available
```

Large external geodata such as `.pbf` files should be downloaded/generated by setup instructions rather than committed.

## Credentials

Before the first public release, rotate credentials that have ever appeared in terminal/debug output as defense in depth. This applies even if a repository scan shows those values were never committed.

Never “redact” a secret by committing a replacement on top of a public history that already contains the secret. History must be rewritten or, preferably for this project, omitted entirely from the new public repository.

## Production-specific strings

A public export should fail or sanitize known deployment identity such as:

- private host/domain names;
- personal e-mail/contact strings that are not intentionally public credits;
- home usernames/hostnames;
- absolute paths containing personal usernames.

Generic paths such as `/opt/immobilien-monitor` are acceptable documentation defaults.

The Nominatim User-Agent must use a configurable contact string rather than a personal address baked into public source.

## Tampermonkey

The private repository preserves the exact tested production userscript.

The public export regenerates a readable userscript with a deliberately invalid example endpoint. Every fork must configure its own endpoint and matching Tampermonkey `@connect` permission.

This prevents a fork from accidentally transmitting viewed listing data to the original operator's server.

## Portal data and tests

Do not publish captured listing pages, archived listing e-mails or a populated property database as project fixtures.

The first public export also excludes the private `app/test_*` regression files because some were created from real production cases. Public regression tests should be rebuilt from **synthetic/minimized fixtures** that contain only the text necessary to exercise parsing behavior.

The project is not affiliated with listing portals. Users are responsible for portal terms, applicable law, data protection and respectful request rates. The browser workflow operates on a page the user intentionally opened in their own browser; it should not be presented as a mechanism for bypassing access controls.

## Repeatable export

Use:

```text
tools/export_public_snapshot.py
```

The exporter copies only intentionally selected tracked source into a new directory, excludes runtime/private paths and production captures, neutralizes deployment-specific strings, regenerates the userscript with safe example endpoints, and fails on high-confidence secret/private patterns.

Known private host/domain strings can be added to the audit without hard-coding them into the exporter itself through:

```text
IMMORADAR_PRIVATE_STRINGS
```

After export:

```bash
cd /path/to/public-export

git init
git add .
git diff --cached --check
```

Then run an independent secret scanner before the first public push. Recommended choices include Gitleaks or TruffleHog, plus a manual review of suspicious identifiers/values.

Do not blindly treat every `TOKEN_KEY` source-code symbol as a secret; verify actual values.

## Fresh public repository

Create the public repository empty and push the sanitized snapshot as its first commit.

Do **not**:

- import the production repository's `.git` directory;
- fork the historical production repository as the public release;
- change the historical repository's visibility to Public.

Suggested release workflow:

```text
private production repo
        |
        +-- backup/checkpoint
        +-- release preparation branch
        +-- export_public_snapshot.py
                  |
                  v
          sanitized directory
                  |
           independent scan
                  |
                  v
         NEW public repository
          first clean commit
```

The preparation branch itself is still part of the private repository's history and is **not** the thing to publish. Only the generated history-free directory crosses the public boundary.

## Final pre-public checklist

- [ ] Production DB/backups excluded.
- [ ] E-mail archives/browser inbox excluded.
- [ ] No real `.env`, token, password, session or private key.
- [ ] No unintended personal contact/hostname/path remains.
- [ ] Production Apache/systemd captures excluded; generic examples only.
- [ ] Public Tampermonkey endpoint is neutral/configurable and not the production server.
- [ ] Production-derived tests/fixtures excluded or replaced with synthetic fixtures.
- [ ] Independent secret scanner reports clean or every finding is manually explained.
- [ ] README/install/docs match the public configuration.
- [ ] AGPL-3.0-or-later license included.
- [ ] New public repository starts with a fresh commit and contains no private production Git history.
- [ ] Credentials exposed outside the repository during historical debugging have been rotated where appropriate.
